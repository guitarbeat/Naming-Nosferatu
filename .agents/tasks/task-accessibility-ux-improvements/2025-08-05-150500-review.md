# Accessibility and reduced-motion hardening across tournament UI

This change systematically addresses two accessibility gaps: framer-motion animations that ignored the `prefers-reduced-motion` user preference, and missing ARIA semantics (live regions, progressbar, landmark labelling, focus management). The approach threads `useReducedMotion()` through five component trees to conditionally strip transform/scale properties from animations while preserving opacity fades, adds `role`/`aria-live` attributes to dynamic content regions, wires Section headings to their parent landmarks via `aria-labelledby`, and auto-focuses the Lightbox close button on mount. A secondary cleanup replaces the lone `any` type with a proper inline interface and downgrades a non-critical `console.error` to `console.warn`.

Watch for: the `prefersReducedMotion` prop-drilling in NameSelector adds coupling without clear benefit over a hook call at the leaf (possible); `role="status"` and `aria-live="polite"` on the same element is redundant but harmless (confirmed); the Lightbox auto-focus fires only on mount, which is correct for a mount-only lightbox but would misbehave if the component were ever kept mounted across open/close toggles (likely).

**Verdict**: APPROVED

## High-level view

Reduced-motion support follows a single pattern everywhere: call `useReducedMotion()` at the component root, then inline ternaries that strip `y`, `scale`, and other transform props from `initial`/`animate` objects, leaving only opacity. The pattern is consistent across HomeSections, NameSelector, TournamentFlow, SearchFilterBar, and Dashboard's EngagementPanel.

ARIA semantics are applied surgically: `role="alert"` on validation errors for immediate announcement, `role="status"` on the tournament-complete container for polite announcement, a proper `progressbar` role on the tournament progress bar, `aria-hidden` on the purely decorative VS divider, and `aria-labelledby` connections between Section landmarks and their headings.

The Lightbox focus-management change auto-focuses the close button via a ref and a mount-only effect. The previous focus target was the backdrop `motion.div` with `onClick={onClose}`, meaning a keyboard user pressing Enter on the focused backdrop would close it accidentally — the close button is a much better target.

Color contrast improvements raise text opacity values across MatchSideCard, TournamentComplete, and TournamentHeader — from `text-white/35`–`text-white/50` up to `text-white/60`–`text-white/75`. Actual WCAG AA compliance depends on the composited alpha against the page background gradient, which isn't verifiable from code alone.

## Reduced-motion pattern and prop-drilling trade-off

In NameSelector, `prefersReducedMotion` is threaded as a prop to two internal sub-components (`AdminActionButton` and `SelectionBadge`):

```tsx
function AdminActionButton({
  ...
  prefersReducedMotion,
}: {
  ...
  prefersReducedMotion: boolean;
}) {
```

Both sub-components are defined in the same file and are not exported. They could call `useReducedMotion()` themselves with no additional cost (the hook simply reads a media query listener that framer-motion already maintains globally). The prop-drilling adds type surface and coupling for no observable benefit.

## ARIA live-region redundancy on tournament completion

The tournament-complete container carries both `role="status"` and `aria-live="polite"`:

```tsx
<div className="..." role="status" aria-live="polite">
```

Per the ARIA spec, `role="status"` has an implicit `aria-live` value of `polite` and an implicit `aria-atomic` of `true`. The explicit `aria-live="polite"` is redundant and could confuse future maintainers into thinking both are required.

## Lightbox focus management edge-case

The existing backdrop `motion.div` has `onClick={onClose}`, so focusing it meant a keyboard user pressing Enter would accidentally close the lightbox. Moving focus to the close button fixes this.

The edge-case: if a parent ever changes to keep the Lightbox mounted and toggle visibility via CSS or a boolean prop, the mount-only effect won't re-fire and focus won't move on subsequent "opens." The current architecture (conditional rendering via AnimatePresence) avoids this, but it's an implicit contract.
